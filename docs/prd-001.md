# PRD-001: YouTube Playlist Player

## Problem

Listening through your own YouTube playlists means either navigating YouTube's full site (built around discovery and recommendations, not a focused listening session) or fumbling in-order playback without a purpose-built player. There's no lightweight, personal tool that just: sign in, browse your playlists, hit play, let it run.

## Goals

- Let one person (the owner) sign into their own Google account and see their YouTube playlists.
- Let them play a playlist jukebox-style: click a video, it plays, and playback auto-advances through the rest of that playlist.
- Keep the tool simple enough to run locally with no hosting, backend, or ongoing maintenance burden.

## Non-goals

- **Multi-user / public access.** This is a personal tool for one person (see [ADR-0003](./adr/0003-client-side-only-spa.md)). No account system, no support for other users signing in with different intent than "this is my own YouTube account."
- **Watch Later / Liked Videos support.** Excluded due to a YouTube Data API limitation, not a product choice — see [ADR-0004](./adr/0004-exclude-special-playlists.md).
- **Cross-playlist or custom queues.** The Queue is always exactly one playlist's videos, in order. No "add to queue" across playlists.
- **Shuffle.** Deferred — repeat-all is in scope, shuffle is not.
- **Search or filtering** within or across playlists.
- **Offline playback or audio extraction.** Playback is always via YouTube's own embedded player; no downloading or stream extraction (see [ADR-0002](./adr/0002-playback-via-iframe-player-api.md)).
- **Caching or persistence of playlist data** across sessions — every load fetches fresh from the API.
- **Deployment/hosting.** Local dev server only for now (`npm run dev`); no production hosting target.

## Users

A single person: the app's owner, signed into their own Google account. The OAuth consent screen runs in Testing mode with the owner (and optionally a few named others) added as test users — no public app review from Google is needed or wanted.

## Functional requirements

### Authentication
- Sign in via Google Identity Services' browser-only OAuth token flow (no backend, no client secret) — see [ADR-0001](./adr/0001-oauth-via-youtube-data-api.md).
- Request only the `youtube.readonly` scope — the app never writes to the account.
- Access token stored in `sessionStorage`; cleared on tab close.
- On token expiry (~1 hour) or a `401` from the API, the user is dropped back to a "Sign in with Google" screen. No silent refresh in this version.
- A "Sign out" control revokes the token and clears the stored session.

### Browsing playlists
- On sign-in, fetch and list the user's own playlists (`playlists.list?mine=true`), fully paginated up front.
- Exclude auto-generated playlists (Watch Later, Liked Videos, Uploads) — only the user's created playlists are listed.
- Selecting a playlist fetches and lists its videos, fully paginated up front.
- Playlist entries that are dead placeholders ("Private video," "Deleted video") are filtered out of the video list entirely.

### Playback
- Clicking a video starts the Queue: that playlist's videos, in order, beginning at the clicked video.
- Playback happens via the YouTube IFrame Player API, rendered in a persistent player bar that stays visible while the user browses other playlists.
- When a video ends, or fails to play (e.g., embedding disabled by the owner), playback automatically advances to the next video in the Queue.
- Controls: play/pause, skip forward, skip back, and a repeat-all toggle (wraps the Queue back to the start when it reaches the end).
- The currently playing video is visually indicated in the video list.

## Success criteria

- Owner can sign in, see their real playlists, click a video, and have it play with working auto-advance to the end of a playlist.
- Skip/prev/repeat controls behave correctly against the Queue.
- Unavailable videos (private/deleted/embed-disabled) never block playback — they're skipped or filtered without user intervention.
- Re-running `npm run dev` after the one-time Google Cloud setup in [README.md](../README.md) requires no further configuration.

## Open questions (deferred, not blocking v1)

- Sign-out/consent-denied/loading-state UX beyond the minimum viable handling already implemented.
- Whether to add Liked Videos support (would need its own fetch path — see ADR-0004).
- Whether to add shuffle, cross-playlist queueing, or search once the core flow is in daily use.
